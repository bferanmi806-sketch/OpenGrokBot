# Security: what is enforced, what is a convention, what is on you

The loudest objections to hosted always-on agents were about custody: an agent that never sleeps, holding your
credentials, on someone else's cloud. Self-hosting answers the custody question. It does **not** answer prompt
injection — that follows an agent wherever it runs. This page is precise about which is which.

## Enforced by the gateway (in code, covered by tests)

| Boundary | How it holds |
|---|---|
| Only you can drive the gateway | Every API call, the live stream, screenshots and screens need the gateway token — a random secret in `gateway/data/auth-token` (mode `0600`). A browser signs in once through the link printed at startup and keeps an `HttpOnly`, `SameSite=Strict` cookie; scripts send `Authorization: Bearer <token>`. |
| Other websites cannot act as you | Anything that changes state, and the WebSocket, must come from the gateway's own origin (or the UI's, `OPENSUPERBOT_WEB_URL`), and requests with a body must be JSON — which no other page can send without a preflight the gateway never answers. A page you happen to visit cannot approve a hold, post into a thread or read the stream. |
| Your network cannot reach it | The gateway listens on `127.0.0.1` unless you set `OPENSUPERBOT_HOST`. |
| A bot cannot approve its own holds | The token never enters a bot's workspace. A bot's shell or browser can reach the host, but cannot authenticate. |
| Only you can grant a standing approval | A rule is created only when you approve a hold with *Always allow…* from your signed-in browser. Its scope is fixed by the gateway: one teammate, one kind, one exact destination, with an expiry you pick. The destination must have the shape of one place — one email address, one channel or handle, one account, page or thread; wildcards, lists, "everyone" and whole services are refused, and so is anything over 200 characters. Destinations are compared whole: case is ignored except in a URL's path. Purchases, bookings and "other" (including every MCP write) can never become rules. Bots have no tool to create, widen or extend one; you revoke them from the computer panel. |
| Rules only cover work you started | A rule lets a hold through only in a turn you started — your message, your decision, your answer, your question to the group — and only while the turn has not seen untrusted external content (`outside-data`): no webhook payload or tainted teammate handoff (`bot_ref`) in the teammate's view, and no browser page read (`browser_goto`, `browser_extract`, `browser_click`, `browser_back`, `browser_screenshot`), connector read, MCP read, or tainted shared wiki search/read (`wiki_search` / `wiki_read`) in that turn. Turns started by a routine, a webhook or a teammate's handoff always ask, and the chip says why. The model is never told which destinations a rule covers. What this does not cover: files you attach, files in the teammate's workspace, shell output, or untrusted text that already landed in an earlier turn's chat history (outside webhook or tainted `bot_ref` cards) do not mark a fresh turn `outside-data` — content from those sources could still steer a hold to a destination you once allowed. Keep standing rules for destinations where a wrong send is cheap. |
| Only work you started changes your setup | `save_memory`, `forget_memory`, `create_routine` and `stop_routine` are offered only in a turn you started — your message, your decision, your answer, your question to the group. In a turn started by a routine, a webhook or a teammate's handoff they are left out of the tool list, refused if the model names them anyway, and the attempt is logged; the teammate can still tell you what it would change. Unlike standing rules, webhook data still in view does not block them in a turn you started, because you are there to see the chip. Handing work to a teammate stays possible from any turn: the receiving turn counts as a handoff and has the same limits. |
| A webhook opens one routine and nothing else | `POST /hooks/routines/:id` (alongside the one-time OAuth callback `GET /oauth/connector/:nonce`) sits outside the gateway token. Each routine has its own random key: sent as a header or `?key=`, or used by GitHub as the secret behind an `X-Hub-Signature-256` signature over the exact body. Both are compared in constant time; a wrong key, a wrong signature and an unknown id all get `404`. A repeated GitHub delivery runs once, and so does a captured signed request replayed under a different delivery id (the signature itself is remembered); a delivery refused because the last run was still going is not counted, so GitHub's redelivery of it runs. Bodies over 1 MB are refused as they arrive, before they are buffered, and at most 16,000 characters reach the model. The body is posted into the thread as an *outside data* card when the teammate picks it up, so you can see what set it off. The key never enters the thread or the model's context — only the computer panel shows it. |
| A payload stays inside its fence | What a webhook delivered reaches the model between two lines that carry the payload's own SHA-256 fingerprint, with every payload line prefixed by `│`. Writing a convincing end-of-payload line from inside would mean finding a text that contains its own hash. |
| An upgrade keeps a way back | Before a schema upgrade the gateway writes a complete copy of the database next to it and keeps the three most recent. It refuses to upgrade if the copy fails. |
| Bots cannot reach each other | All bot computers share one Docker network with container-to-container traffic switched off. And because on Docker Desktop a container can still reach ports published on the host, everything a computer publishes wants that computer's own secret: its shell/file shim and its browser control port (CDP) a per-container token, its screen a per-container VNC password. |
| Each Docker computer is a cage | Its own container with memory, CPU and process limits, `no-new-privileges`, and only its own workspace and isolated `/var/lib/bot-browser` profile mounted. Every port is published to `127.0.0.1` only, and the shim strips `SHIM_TOKEN` and `VNC_PASSWORD` from commands it runs. |
| A local computer's files stay in its folder | `read_file` and `write_file` resolve inside that teammate's folder — `/workspace` maps to it — and a path that leaves it by name or through a symlink is refused. Its browser profile lives outside that folder, downloads land inside `<workspace>/downloads`, and `browser_goto` accepts only `http:` / `https:` URLs (with `file:` requests aborted in Chrome), so the teammate cannot read your disk or its own cookie store through the browser or file tools. |
| A local computer's commands are off, then caged | Commands are off until you turn them on for that teammate in its panel. On, they run under Seatbelt (macOS) or bubblewrap (Linux): they can write only the teammate's folder and a private tmp; your whole home directory — keys, documents, other projects, your own browser profile, the gateway's data dir — is unreadable, except the runtime managers (`~/.nvm`, `~/.volta`, `~/.pyenv`, `~/.cargo/bin`, …) that are put back read-only; a data dir outside your home is hidden too; `HOME` points at the folder and the environment is a short whitelist. The switch refuses to turn on until a self-check shows the sandbox blocks a write outside the folder, a read of the gateway token and a listing of your home directory. A command that outlives its timeout, or that you stop, is killed with its whole process group. |
| A file you send cannot run as a page | The gateway decides what an uploaded file is from its content, not from the type the client declared, and accepts only images, PDFs, plain text and Markdown; a page dressed up as an image is refused. It serves uploads with `nosniff` and a sandboxing `Content-Security-Policy`, images inline and everything else as a download. An upload is stored under a random id, never under the name it came with. |
| A PDF you send cannot take the gateway down | A PDF's text is extracted in a separate thread with a memory ceiling, a 20-second limit, and caps of 200 pages and 2 million characters. A document that breaks the parser, or runs into a limit, is stored without text and reported as such; the upload itself still succeeds and the gateway keeps running. Pages are not rendered and scripts in the document are not run. |
| A bot cannot steer where your files land | The original of a file you send stays in `<data>/uploads`, outside every workspace. The copy for a teammate goes onto its computer through the computer itself: into a container through Docker's archive API, where paths resolve inside the container, and onto a local computer through the same folder check as `write_file`, creating a new file only and never following a link at the name. The gateway does not write into a container's mounted folder from the host, where a link planted by the bot would point at your own disk. |
| A bot cannot put code in front of you | The screen page and its noVNC code are served by the gateway from its own copy; only the raw VNC stream comes from the bot's computer. Nothing a bot changes inside its container reaches your browser as a page. |
| Standing rules only change through the chip | `MEMORY.md` lives outside the bot's workspace. The only ways to change it are `save_memory`, `forget_memory`, accepting a `rule_proposal` card, and the remove button in the computer panel, and each of them posts a diff chip; a `MEMORY.md` a bot writes into its own workspace is ignored. Screenshots — the evidence — are stored outside it too. |
| Controlled Dreaming never auto-writes `MEMORY.md` | Both `propose_memory_rule` (capped at one created proposal per turn) and the 14-day repeated-discard detector (≥ 2 operator discards for the same `(kind, target)` or `(kind, action)`) only post an editable `rule_proposal` card in SQLite (`rule_proposals`) — never touching `MEMORY.md` until you explicitly click *Save to MEMORY.md*. Proposed and edited rules are sanitized into a single line (CR/LF, control characters and leading bullet markers stripped, max 300 characters) and deduplicated against existing memory, pending proposals and previously dismissed proposals. For `propose_memory_rule`, the gateway — never the model — computes `sourceTainted` from `turnTainted` or `origin === 'webhook'` and displays an amber *External source — review carefully* warning badge on the card. |
| Handoffs are allowlisted | By default only the chief of staff can reach everyone. Peer directions need `OPENSUPERBOT_A2A_ALLOW`, and relays stop after two hops. |
| A watch routine cannot act | Its turns are offered only read-only tools — including if you answer a question it asked with `ask_operator` — and any other tool the model names is refused by the gateway: no shell, no writing files, no clicking, typing or key presses in the browser, no connector writes or drafts, no MCP write tools, no wiki writes, no handoffs, no changes to rules or routines. What it holds never matches a standing rule. It can still load pages, so it can still be steered by what it reads; it just has nothing to act with. |
| A prepare routine gathers context without acting outward | Its turns are offered only the `watch` read-only tool set plus `wiki_upsert`, `wiki_patch` and workspace `write_file` (alongside read-only MCP tools), and that capability boundary is preserved across `ask_operator` resumptions. Any other tool the model names is refused at runtime by the gateway: no `shell`, no interactive browser mutations (`browser_click`, `browser_type`, `browser_press`), no external connector writes or drafts, no MCP write tools, no teammate relays (`message_bot`), and no operator-only setup tools (`save_memory`, `forget_memory`, `create_routine`, `stop_routine`). What it holds never matches a standing rule. |
| Quiet Hours buffers only non-urgent scheduled checks | When opt-in Quiet Hours are enabled (`quietHoursStart`–`quietHoursEnd`, evaluated in the gateway timezone), only non-urgent scheduled `watch` and `prepare` reports and final text replies are buffered in SQLite (`quiet_digest_items`) and flushed together as one Morning Digest card when the window ends, when Quiet Hours are disabled, or when you click *Deliver now*. Urgent alerts (`urgent: true` on `message_user`), approvals (`hold_for_approval` and connector/MCP write holds), `ask_operator` questions, login requests, error/budget notices, operator-started turns, `act` routines, webhook routines and manual runs (`force: true`) always break through immediately. |
| A batch is approved item by item | The gateway stores the exact items a bot held and the ones you left ticked; the bot is told that subset and nothing else. A batch can never become a standing rule. |
| Per-teammate connector isolation | Connected app accounts (`connector_accounts`) grant zero access by default: a teammate only sees connector tools and accounts explicitly listed for it in `bot_connectors` (and when two or more accounts in the same domain are granted, every call must name the exact `account` id). Neither `<data>/composio-key` (`0600` on macOS and Linux; owner-only ACL on Windows) nor upstream OAuth tokens ever enter any teammate container, local workspace, command sandbox or model prompt. |
| Gateway-executed connector writes & draft snapshot lock | Outward connector writes (`mail_send`, `mail_reply`, `mail_archive`, `calendar_create_event`, `calendar_update_event`, `notion_create_page`, `notion_append`, `slack_send_message`) are intercepted in gateway code before calling the upstream provider. Approval chips are built strictly from real parameters — reading back actual draft contents on `mail_send({ draftId })` and `Reply-To` / sender / recipient headers on `mail_reply`, locking held `draftId` snapshots against in-place `mail_draft` mutation while pending, and freezing the exact request in SQLite. On *Approve* (or 👍), the gateway re-verifies the teammate's grant, account status and draft snapshot integrity, then executes the frozen request directly in a single attempt (reporting `uncertain` without auto-retrying on timeout or `5xx` to prevent duplicate sends). |
| Connector `outside-data` taint & OTP/reset-link redaction | Reading any connector read tool (`mail_list`, `mail_read`, `calendar_list`, `notion_search`, `notion_read_page`, `slack_list_channels`, `slack_read_messages`) taints that turn as `outside-data`, so standing *Always allow…* rules cannot auto-approve subsequent `hold_for_approval` holds or connector writes in that turn. `mail_list` also hides automated/bulk mail unless `includeAutomated: true`, and `mail_read` strips HTML scripts/styles and click-tracking URL parameters (`utm_*`, `fbclid`, `gclid`, long opaque tokens, …) and redacts 4–8 digit OTP codes (`[redacted-otp]`) and password-reset / magic-login / verification URLs (`[redacted-security-link]`) before text reaches the model. |
| Per-teammate MCP server isolation & sanitized `stdio` host boundary | Configured MCP servers (`mcp_servers`) grant zero access by default: a teammate only sees `mcp__<server>__<tool>` tools from enabled servers explicitly listed for it in `bot_mcp_servers`, and models have no tool or endpoint to create, edit or delete MCP servers. Secrets in `<data>/mcp-secrets.json` (`0600` on macOS and Linux; owner-only ACL on Windows) never enter any teammate container, local workspace, command sandbox or model prompt, and any secret values echoed in `stderr` or HTTP errors are redacted (`[REDACTED]`) before reaching `last_error` or tool output. When spawning a `stdio` server (`shell: false`), the gateway builds the child environment from a short OS allowlist plus that server's explicit `env` — stripping `OPENSUPERBOT_*`, model API keys, Composio keys and gateway tokens — and advertises empty client capabilities (`{}`), refusing server-initiated `sampling/createMessage` or `roots/list` requests. |
| Gateway-executed MCP writes & 3-tier read/write policy | Every discovered MCP tool defaults to `write` (held for approval and hidden from `watch` routines) unless you explicitly mark it `read` in `toolPolicies` or enable `trustReadOnlyHint` on that server (and even then, a tool with `destructiveHint: true` stays `write` unless overridden individually). Every `write` MCP call is intercepted in gateway code before reaching the server and stored as an `other` hold (`canRemember = false`, so MCP writes always ask item by item and never become standing rules) with its exact `FrozenMcpExecution` arguments frozen in SQLite. On *Approve* (or 👍), the gateway re-verifies that the server still exists, is enabled and is still granted to that teammate, then executes `tools/call` directly in a single attempt — recording `uncertain` without auto-retrying if the process exits, stream drops, `5xx` returns or timeout fires after dispatch. |
| MCP `outside-data` taint & legacy SSE same-origin check | Calling any `read` MCP tool taints that turn as `outside-data` (omitting external image, audio and binary blocks from text tool output and capping output at 16,000 characters), so standing *Always allow…* rules cannot auto-approve subsequent `hold_for_approval` holds or connector writes in that turn (and the post-approval follow-up turn after an MCP write starts tainted as well). Remote `Streamable HTTP` servers validate `http:` / `https:` URLs (refusing embedded credentials and forbidden framing headers) and, when falling back to `2024-11-05` HTTP+SSE, enforce `endpointUrl.origin === baseUrl.origin` before posting requests — preventing a cross-origin `endpoint` event from leaking custom `Authorization` headers or steering requests elsewhere. |
| Per-teammate Credential Vault & zero-exposure fill | Vault items (`vault_items`) grant zero access by default: a teammate only sees metadata (`id`, `slug`, `allowedDomains`, field names — never raw values) for items explicitly granted in `bot_vault_items`, and `browser_fill_secret` is excluded from `watch` routines. Raw values live only in `<data>/vault-secrets.json` (`0600` on macOS and Linux; owner-only ACL on Windows) outside SQLite and outside every container/sandbox. Before filling, the gateway verifies HTTPS (or an explicitly listed loopback host), matches `page.url()` against strict `allowedDomains` (rejecting broad wildcards such as `*`, `*.com`, or `*.co.uk`), and enforces that `secret`-kind fields only fill `<input type="password">` elements. Items set to `always` — or any `on_taint` item during a routine, webhook, handoff, or `outside-data` tainted turn — are held as gateway-executed `vault_fill` approvals (`canRemember = false`, zero plaintext in SQLite) that re-verify grant and exact `expectedOrigin` before filling (generating live RFC 6238 TOTP codes at fill time). Subsequent computer tool outputs in that turn are redacted against used vault secrets. |
| Today Feed taint preservation & read-only Idea Incubation | Feed cards published via `publish_feed` (capped at 3 per turn) or projected from `watch` / `feed`-surfaced routines automatically inherit `tainted = 1` whenever the turn was not operator-started or touched `outside-data` — the model cannot clear that flag. Promoting a tainted proposal into the Idea Inbox preserves `tainted = 1`, follow-up/dispatch turns start tainted so standing approval rules cannot silently fire, and clicking **Incubate (read-only)** always runs the chosen teammate in strict `watch` mode (read-only tools only, zero writes or external actions). |
| Gateway-owned Goals & anti-tampering authority split | Long-term goals, milestones and progress logs live strictly in gateway SQLite (`goals`, `goal_milestones`, `goal_updates`), never in a bot's workspace. `manage_goal` (creating/editing goals, changing success criteria or status, adding/completing/removing milestones) is restricted to `OPERATOR_ONLY_TOOL_NAMES` (omitted and refused in routine, webhook, relay and `watch` turns). Non-`watch` participating teammates may only call `update_goal_progress` (capped at 2 notes per turn, active assigned goals only), which never mutates definitions or milestones and automatically marks non-operator / `outside-data` notes `tainted = 1`. Every tool-driven change posts a visible `goal_updated` diff chip and lands in the SQLite `actions` log; active goal prompt injection is hard-capped at 2,400 characters; pausing, finishing or archiving a goal removes it from prompts and automatically skips scheduled runs of linked routines (`routines.goal_id`). |
| Spaces (declarative blocks + sandboxed HTML) & per-teammate role isolation | Live Spaces (`spaces`, `space_items`, `space_bots`) validate every schema through `parseSpaceSchema()` across 10 block types (`metrics`, `table`, `kanban`, `checklist`, `timeline`, `chart`, `markdown`, `action_bar`, `cards`, `html`) — rejecting unknown block types, prototype-pollution keys, non-`http(s)` table/card links, unsafe image URLs, and oversized payloads (<=12 blocks / 256 KB schema / 120 KB per HTML block / 200 items per space). Any `html` block renders strictly inside an opaque null-origin `<iframe sandbox="allow-scripts">` (no `allow-same-origin`, `allow-top-navigation`, `allow-forms`, or `allow-popups`) with an injected CSP (`default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src https: http: data: blob:; font-src data:; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`), so Space scripts can never access gateway cookies, DOM, APIs, or external network endpoints; links inside HTML blocks post back to the host and open only after `http(s)` validation. Teammates have zero access by default until explicitly granted `viewer` or `editor` in `space_bots`. `manage_space` (creating spaces or editing layouts, HTML blocks, and `action_bar` buttons) is restricted to `OPERATOR_ONLY_TOOL_NAMES` so untrusted pages or routines can never forge HTML or action buttons; `space_read` is safe in `watch` runs (and propagates `outside-data` taint if the space holds tainted items); `space_upsert_item` / `space_delete_item` require `editor` access in non-`watch` turns (capped at 10 writes per turn) and automatically mark non-operator / `outside-data` records `tainted = 1` with visible `space_updated` audit chips. Action buttons execute only prompts stored in the gateway database. |
| Operator-edited approvals (*Edit & Approve*) | Pending connector writes (`mail_send`, `mail_reply`, `slack_send_message`, `notion_create_page`, `notion_append`, `calendar_create_event`, `calendar_update_event`), MCP write tools and non-batch `hold_for_approval` drafts can be edited inline before approving. Every edit is validated atomically *before* settling the approval — rejecting empty required fields, CR/LF email header injection, oversized payloads, `__proto__` keys or tampered read-only identifiers (`connectorId`, `serverId`, `draftId`, `messageId`, `eventId`, …) with HTTP `400` (`invalid_edit`) while keeping the approval `pending`. Editing a `draftId` email still verifies the remote draft against its pre-edit TOCTOU snapshot before updating the draft in-place and sending it once. Any standing rule (`remember`) submitted with an edit is re-evaluated against the post-edit destination before settlement, and edited approvals record `edited: true` on the chip and timeline plus `(edited by you)` in the SQLite action log. |
| 共享技能归你掌控且内置只读兜底（Shared & Built-in Skills） | 共享技能由随网关与桌面包只读发布的 6 份预置手册（`gateway/skills/*.md`：`meeting-minutes`、`research-brief`、`spreadsheet-analysis`、`doc-drafting`、`slide-outline`、`careful-browsing`）与操作者在 `<data>/skills/*.md` 编写的自定义手册双层组成，两者均位于所有同事的 Docker 容器与本机工作区沙箱之外，同事没有任何工具可创建、修改或删除技能文件。列举（`listSkills` / `listMergedSkills`）与按名读取（`readSkill` / `readMergedSkill` 及 `agent.ts` 中的 `execReadSkill` 白名单前置拦截）共享同一套合并目录解析：（1）强制通过 `/^[a-z0-9][a-z0-9_-]{0,63}$/` 文件名校验，仅允许读取合并目录中实际列出的有效技能；（2）对目录与文件执行 `lstat`、要求 `Dirent.isFile()`（拒绝符号链接目录、软链文件、FIFO 管道与设备节点），并以 `O_NOFOLLOW` 打开文件描述符二次核验普通文件身份与 `256 KB` 体积上限，彻底阻断软链逃逸读取 `../auth-token` 等敏感文件或超大文件拖垮内存；（3）操作者在 `<data>/skills/<name>.md` 放置的同名合法文件始终优先覆盖内置版本（升级应用不丢失修改），并在 `MAX_SKILLS = 50` 总上限下优先保底用户自定义技能配额（溢出淘汰的内置项亦不可通过 `read_skill` 绕过读取）；（4）本机受信任技能手册按需读取不触发 `outside-data` 污点，其中 `careful-browsing` 显式强化将网页全部正文视为不可信外部数据、遇登录墙/MFA/验证码立即交由 `ask_for_login` 接管、以及不可逆提交前暂停请求审批的操作纪律。 |
| Shared team wiki (`<data>/wiki/`) | Shared factual entity pages (`contact`, `client`, `project`, `topic`) live in SQLite and are mirrored atomically to `<data>/wiki/<kind>/<slug>.md` outside every teammate's workspace, Docker container and local command sandbox; bots access the wiki only through gateway tools (`wiki_search`, `wiki_read`, `wiki_upsert`, `wiki_patch`). `wiki_patch` applies validated section-level updates (preserving untouched list entries and `[#msg:<id>]` citations unless an explicit drop reason is supplied) and writes `## Change Log` deterministically in gateway code (stripping any model-supplied changelog); `watch` routines remain strictly read-only (`wiki_upsert` and `wiki_patch` are left out of tool schemas and refused at runtime). Dual-list `wiki_search` returns curated `pages` alongside ranked conversation `originals` from `messages_fts` strictly bounded to `accessibleThreadIds(db, botId)` (`dm:<botId>` plus that teammate's group memberships), so one teammate can never read another teammate's private DM history, while webhook hits stay wrapped in SHA-256 `<<<webhook` fences and approval cards stay summarized. Deterministic secret scrubbing redacts raw API keys and bearer tokens (`sk-`, `sk-ant-`, `xai-`, `AIza`, `gsk_`, `cmp_`, `ghp_`, `github_pat_`, `xoxb-`, `Bearer …`) before `wiki_patch` or auto-sync writes reach SQLite, FTS or disk mirrors. Any page created or updated during an `outside-data` turn or from a webhook — and any idle (`P3 low`-priority) or manual (**Sync from chats**) chat-to-Wiki auto-sync pass whose thread window contains a webhook message, tainted `bot_ref` relay, or external read tool action (`web_*`, `browser_*`, connector reads, `mcp__*`) — marks `source_tainted = 1` (and neither teammates nor `auto-sync` can clear that flag on subsequent edits); reading or matching a tainted page or untrusted original via `wiki_read` or `wiki_search` marks the turn `outside-data` — propagating across A2A relays and group rounds — so untrusted external content cannot be laundered through the wiki to bypass standing *Always allow…* rules until you review and save the page in **Team wiki**. Behavioral rules stay exclusively in tamper-evident `MEMORY.md`, never in the wiki. |
| Background tasks stay isolated (`origin: 'background'`) | Offloaded tasks run in a per-teammate secondary lane (`1` running + up to `5` queued, at `background` local-LLM priority so interactive chat preempts between steps) with `origin: 'background'`. They cannot recursively spawn, steer or cancel background tasks (`delegate_background_task`, `steer_background_task`, `cancel_background_task` are omitted and refused at runtime), cannot mutate standing rules or routines (`save_memory`, `forget_memory`, `create_routine`, `stop_routine` are blocked), and every outward action (`hold_for_approval`, connector writes, MCP writes) always waits for your approval — never matching standing *Always allow…* rules (recording `ruleHeld: 'background'` whenever a standing rule would otherwise match). External-data taint propagation (`outside-data` and `sourceTainted` on wiki writes, `propose_memory_rule` and `message_bot`) is preserved identically, including taint propagated from tainted foreground turns through `delegate_background_task` and `steer_background_task`. Browser tools (`browser_goto`, `browser_extract`, `browser_click`, `browser_type`, `browser_press`, `browser_scroll`, `browser_back`, `browser_screenshot`, `ask_for_login`) acquire a lazy per-bot browser lease mutex so foreground chat and background tasks never clobber the same persistent page; non-browser tools run freely in parallel, and workflow recording (`POST /api/bots/:botId/workflows/recording`) and replay (`POST /api/bots/:botId/workflows/:workflowId/run`) return HTTP `409` (`browser_in_use`) while a background task holds the lease. |
| Group team charter (`team.md`) & DAG dispatch pipelines | Each group's shared charter lives outside every teammate's workspace, container and command sandbox at `<data>/groups/<safe-key>/team.md` (with traversal-safe, Windows-safe naming and a SHA-256 suffix) and is editable only by you via `GET`/`PUT /api/threads/:threadId/team` (max 16,384 characters); bots have no tool to write it. Only Chief in an operator-started `act` group turn can call `create_dispatch_plan`, which validates an acyclic DAG (up to 12 steps, restricted to members of that group) and posts a `draft` pipeline card that never executes until you explicitly click *Start pipeline* (`POST /api/dispatch-plans/:id/start`). Every pipeline step runs with `origin: 'relay'`, `priority: 'background'`, `trigger: 'pipeline'` and `isPipelineStep: true` — withholding all standing *Always allow…* rules (recording `ruleHeld: 'relay'`), omitting operator-only setup tools, and forbidding recursive `create_dispatch_plan` or `delegate_background_task` calls. `outside-data` taint propagates across DAG edges (`plan.sourceTainted` or any upstream `outputTainted` starts downstream steps tainted) and is preserved across approval/question pauses and resumptions. |

## A convention, not a wall

**对外动作审批门禁与静态护栏的边界。** 每位同事的系统提示词与 `AGENTS.md` 硬边界都要求在任何对外动作发生前先调用 `hold_for_approval` 等待操作者确认。在网关代码层面，内置 OAuth 连接器写操作、MCP 写工具、凭证库自动填充，以及命中高危确定性护栏（`action-guardrail`）的 6 类高危 `shell` 命令与敏感网页提交（结账付款、永久删除、对外发送/发布及高敏路径回车提交）均由网关强制拦截、冻结在 `execution_json` 中并坚持一件一问（`canRemember = false`，浏览器动作额外校验 `expectedOrigin` 防跨源漂移），经批准后由网关单次直执。但需客观认识其边界：基于命令语法树展开与文案/路径特征的确定性护栏旨在与底层 OS（Seatbelt / bubblewrap）及 Docker 容器沙箱形成**纵深防御**，并不能替代沙箱本身——模型在工作区内编写的自定义混淆脚本，或已登录第三方站点上命名非常规的自研前端按钮，仍可能绕过静态特征匹配而无需经过 `hold_for_approval`。因此请务必配合沙箱隔离并遵守下方第 1 条原则（为同事分配独立专用账号），让任何潜在误操作的爆炸半径可控。

**What a standing approval trusts.** For `hold_for_approval` in the browser or shell, a rule matches the kind and
destination the bot itself declares when it holds an action, and then the bot performs the action on its own
computer; the gateway decides whether to ask you again, not what the bot does next (whereas for built-in connector
and MCP write tools, the gateway freezes the exact call parameters and executes the call itself — and MCP writes
never match standing rules at all). Outside
input cannot start a turn in which a rule applies, reading untrusted external content in the turn — webhook payloads,
browser page reads (`browser_goto` / `browser_extract` / `browser_click` / `browser_back` / `browser_screenshot`),
connector reads, MCP reads, tainted shared wiki searches/reads, or tainted `bot_ref` handoffs — withholds rules as
`outside-data`, and the bot is not told which destinations its rules cover. Still, within an untainted turn you
started, a bot that mislabels a `hold_for_approval` action, by mistake or because of an attached file, workspace file
or shell output it read, could still slip one past a rule. So rules save you waiting on a teammate you already trust
with that destination; they do not make the approval gate stronger. Keep them narrow and short-lived.

**Treating what it reads as data.** Bots are told that pages, files and emails are data, never orders, and a
webhook's body arrives explicitly labelled as data from another system. Prompt injection against tool-using
agents is still an unsolved problem industry-wide.

**A file you send is read like any other file.** What an attached file says reaches the teammate the way a file in its
workspace does: as data it was told not to take orders from. Unlike reading a web page, connector, MCP read tool,
webhook payload, tainted wiki page or tainted `bot_ref` handoff — which mark the turn `outside-data` and withhold
standing rules — a turn in which the teammate reads a file you attached stays an untainted turn you started, so your
standing approvals and its rule and routine tools stay available in it. If you forward a document from someone you do
not trust, treat it with the same caution as untrusted external content. An image is shown to the model as you sent
it, metadata included.

**Forgetting is visible, not approved.** In a turn you started, a bot can drop a standing rule with `forget_memory`
without asking you first, the same way it can save one. Turns started by a routine, a webhook or a teammate cannot
change rules at all. Every removal posts a red diff chip in its thread, so a rule that vanished because of something
the bot read shows up there.

## Rules for you

1. **Give bots their own accounts, never yours.** Separate email, separate calendar, invited only into what
   they need. A bot with its own account has a blast radius; a bot with yours has your life.
2. **Sign in to only what the job needs.** Sessions live in the bot's browser profile on your disk
   (`gateway/data/bots/<id>/browser` from source, or inside the container for Docker), and they are as powerful as
   the account behind them.
3. **Keep the gateway on loopback.** For remote access, tunnel — see [always-on.md](always-on.md). If you
   must bind `0.0.0.0`, the token still guards it, but put TLS in front.
4. **Cap spend twice**: a limit on the API key at your provider, and `OPENSUPERBOT_DAILY_TOKENS` here.
5. **Rotate the token if it leaked**: delete `<data>/auth-token` and restart. Every browser signs in again.
6. **Treat a webhook address like a password.** Anyone holding it can wake that routine with any body. If one
   leaked, delete the routine and ask for a new one.

### Composio custody boundary

Unlike local model keys, gateway tokens and browser profiles — which never leave your disk and need zero third-party middlemen — **Connectors → Apps** (`Gmail`, `Outlook`, `Google Calendar`, `Outlook Calendar`, `Notion`, `Slack`) is opt-in. When you configure the Composio connector driver and authorize an app, `<data>/composio-key` stays `0600` on your disk (owner-only ACL on Windows), while the OAuth refresh and access tokens for those connected apps are vaulted by Composio's service (`backend.composio.dev`, or `OPENSUPERBOT_COMPOSIO_BASE`) and connector API requests transit Composio to reach the upstream provider. Leave **Apps** unconfigured if you want every credential and session to stay strictly on your own machine.

### MCP servers (`stdio` and `Streamable HTTP`) host boundary

Standard MCP servers configured in **Connectors → MCP** keep every credential on your own machine: `<data>/mcp-secrets.json` is written atomically at `0600` (owner-only ACL on Windows) outside SQLite and outside every teammate's workspace, container and command sandbox, and remote `Streamable HTTP` servers (including `2024-11-05` HTTP+SSE fallback, which enforces a strict same-origin check on `endpoint` redirects before sending headers) connect directly from the gateway to the URL you configured with zero third-party relay.

Know the host boundary for local `stdio` servers before adding one: a `stdio` MCP subprocess (`npx`, `uvx`, or a local binary) runs **as your user on the gateway host**, outside any teammate's Seatbelt/bubblewrap command sandbox or Docker container. That is why only you — signed in to the gateway — can add, edit, import or delete MCP servers, why models have no tool to configure them, and why the gateway spawns `stdio` children with `shell: false` and strips `OPENSUPERBOT_*`, model API keys, Composio keys and gateway tokens from their environment (passing only a short OS baseline allowlist plus the explicit `env` keys you set for that server). Only connect `stdio` servers whose code you trust to run on the host. Regardless of transport, every MCP tool defaults to `write` (`kind: 'other'`, never auto-remembered into a standing rule, executed once by the gateway after *Approve* with `uncertain` non-replay on mid-flight failure), and every `read` MCP tool marks the turn `outside-data` so external output cannot trigger standing rules.

## The desktop app

The Electron shell ([desktop.md](desktop.md)) wraps the same gateway without giving web content desktop privileges:

- **Sandboxed renderer, no Node.** Every window runs with `contextIsolation: true`, `sandbox: true`,
  `nodeIntegration: false`, `nodeIntegrationInSubFrames: false` and `webviewTag: false`.
- **Cookie sign-in, no token in URLs or logs.** Main reads `OPENSUPERBOT_TOKEN` or `<data>/auth-token` directly and
  sets the `HttpOnly`, `SameSite=Strict` session cookie for `http://127.0.0.1:<port>` before loading the UI. Logs
  (`logs/gateway.log`) and copied diagnostics scrub gateway tokens, `?key=` query strings, `Bearer` headers and `sk-` /
  `xai-` / `AIza` / `gsk_` keys.
- **Narrow, origin-checked preload.** Only the main window receives `window.opensuperbot`, frozen to `info()` and
  `loginItem.get()` / `loginItem.set(on)`. Every `ipcMain` handler checks `senderFrame` and rejects calls from
  anything other than the top-level gateway loopback page (`data:` error pages, iframes and other origins are refused
  and logged).
- **Locked navigation and permissions.** Windows and subframes may navigate or redirect only to the gateway's loopback
  origin (`http:` / `https:` links elsewhere open in your system browser; `file:`, `javascript:` and custom schemes are
  blocked). Only `notifications` and `clipboard-sanitized-write` are granted to the gateway's page; camera, microphone,
  geolocation and clipboard reading are denied.
- **One opt-out release check, no auto-updater.** The macOS build is ad-hoc signed (not notarized) and Linux packages
  are not signed by a repository key, so the app never downloads or installs code updates automatically. When
  **Check for a newer version on startup** is enabled in Settings, startup sends one `GET` to
  `https://api.github.com/repos/wolfqing/OpenSuperBot/releases/latest` with no account or machine id, accepts only
  `X.Y.Z` release tags whose page is under `https://github.com/wolfqing/OpenSuperBot/releases/`, and shows a download
  link. Turning the setting off stops the request completely.
- **No `--no-sandbox` fallback on Linux.** On Ubuntu 24.04+, the `.deb` installs narrow AppArmor `userns` profiles for
  `/opt/OpenSuperBot/opensuperbot`, its downloaded Chrome for Testing, and `/usr/bin/bwrap`. Under an AppImage where
  AppArmor blocks unprivileged user namespaces, the commands switch stays locked and explains why rather than running
  commands or browsers without a sandbox.

## Local computers

A local computer is weaker than a container in ways you should know before you give one an account that matters:

- **It runs as you.** The browser and any command run as your user on your machine. The sandbox confines the file
  system, not the network: a command can reach anything your machine can, including services on `localhost`. It
  cannot read the gateway token, so it cannot drive the gateway — but a service of yours that trusts localhost
  without a password is reachable.
- **System services stay partly reachable.** The sandbox confines files, not the whole operating system: a command can
  read system libraries, `/opt` and `/etc` (though `/Volumes` and host `/tmp` are hidden), and on macOS Seatbelt blocks
  pasteboard, LaunchServices and AppleEvents Mach services and cross-sandbox signals, while other system IPC remains
  reachable.
- **No resource limits.** Nothing caps a local teammate's memory or CPU; a runaway command is killed only by its
  timeout (ten minutes at most) or the stop button.
- **The profile is a file.** The teammate's cookies live under `<data>/bots/<id>/browser`, readable by any program
  running as your user — the same standing as your own browser profile, no better.
- **Chromium's own sandbox stays on**, which it cannot inside a container. Pages the teammate visits get the
  protection your own browser gives you.
- **A file placed on a local computer goes through a check, not a wall.** The gateway checks that the `uploads/`
  path stays inside the teammate's folder and refuses to follow a link at the file name, as `write_file` does. A
  teammate with commands on could in principle swap a folder for a link between the check and the write; a
  container computer has no such gap, because there the path is resolved inside the container.
- **On Windows, a local computer has no commands.** It gets the browser and the folder; Windows has no sandbox as
  mature as the two above, so the switch for commands stays off. File access is the gateway's own check, which on
  Windows also refuses other drives, network shares, device names such as `CON`, and alternate data streams.

If a job needs a Linux of its own, software installed, or stronger isolation, give that teammate a Docker computer.

## What self-hosting buys you

| Risk | Hosted (Grok Bot) | Self-hosted (this repo) |
|---|---|---|
| Where your sessions live | the vendor's cloud VM | your disk (browser profiles and `<data>/mcp-secrets.json`); Composio only for apps you opt in to via Connectors |
| Who can subpoena, breach or train on them | the vendor | you (plus whichever remote MCP endpoints or Composio apps you opt in to) |
| Kill switch | a support ticket | the stop button, `docker stop`, or the power cable |
| Audit trail | what the vendor shows you | every message and every action in SQLite on your disk |

## The threat you still own

If a workflow would make a bot both read strangers' input **and** act outward, keep a human decision in the
loop — or redesign the workflow. The approval chip is where that decision happens; keep it meaningful by giving
bots accounts whose worst case you can live with.
